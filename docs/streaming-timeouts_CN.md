# 长请求、入口超时与流式心跳

当入口代理限制源站的静默等待时间时，模型仍在处理并不代表调用方已经收到响应。非流式 Chat Completions 会聚合完整结果后才输出 JSON；在此期间发生上游重试，也可能超过入口的读取超时。

## 流式请求

对需要长时间推理的请求，调用方应发送 `stream: true`，持续读取 SSE。CliRelay 在等待流式初始化、账号排队、上游响应以及后续流数据期间发送注释心跳：

```text
: keep-alive

```

`streaming.keepalive-seconds` 默认是 15 秒；0 使用默认值，负数关闭。心跳不代表模型已经输出内容，不占用上游尝试次数，也不把失败阶段从 `before_output` 改为 `after_output`。

日志中的网络首字节时间仍会记录心跳到达；用量中的首次应用数据时间跳过这些服务器心跳，等待真正的应用响应。后者沿用首次应用写入的定义，并不是对每个协议严格解析后的首个文本 token。

第一次心跳会提交 HTTP 200 和 `text/event-stream`。如果错误发生在此之前，接口仍返回原有 HTTP 错误码与 JSON；如果错误发生在心跳之后，接口发送对应协议的 SSE 错误，并结束流，不发送成功终止标记。调用方必须检查流内错误和完整终止信号，不能仅以 HTTP 200 判定成功。

调用方可以在内存中聚合文本，完整结束后一次展示。Chat Completions 客户端应处理 `choices[].delta`、`finish_reason`、`[DONE]` 和可选用量帧；Responses 客户端应检查完成或失败事件。意外 EOF 应视为不完整响应。工具调用的参数需要按调用索引拼接，完整结束并校验后才能执行；中途断流不能触发工具执行。

## 非流式请求

本次修复不把 `stream: false` 自动改成 SSE，也不默认向 JSON 响应写入空白保活。JSON 空白虽然通常可以被解析，但提前输出会固定 HTTP 200，使之后的错误无法继续使用原 HTTP 状态码。

严格要求单次 JSON 和最终 HTTP 错误码的调用方，需要选择支持其处理时长的入口，或使用异步任务与结果查询。仅缩短服务端截止时间只能让失败更可控，不能使超长任务成功；仅增加上游重试次数可能进一步延长静默等待。

## 验证范围

回归测试应覆盖初始化和首包等待、上游重试、快速错误的 HTTP 状态码、心跳后的协议错误、关闭心跳、客户端取消，以及模型回退诊断和请求终态记录。超过入口限制的模拟慢请求需要同时检查首字节时间、最大相邻读取间隔、最终内容与终止信号。
